- 結果：

  読んだ問題（3 件とも astropy/astropy。データセットの難易度欄はどれも「15 min - 1 hour」）

  | ID | 問題の要約 | 正解のパッチ | 判定に使うテスト |
  |---|---|---|---|
  | `astropy__astropy-12907` | `separability_matrix` が、入れ子にした CompoundModel（例：`Pix2Sky_TAN() & cm`）の出力と入力の分離可能性を誤って計算する。同じモデルを入れ子にせずに書くと正しく出る | 1 ファイル。`_cstack` の 1 行（`= 1` を `= right` に変える） | FAIL_TO_PASS 2 件、PASS_TO_PASS 13 件 |
  | `astropy__astropy-13033` | TimeSeries で必須の列を消したとき、エラー文が「'time' を先頭に期待したが 'time' があった」のように矛盾した内容になる | 1 ファイル。約 11 行追加、3 行削除 | FAIL_TO_PASS 1 件、PASS_TO_PASS 20 件 |
  | `astropy__astropy-13236` | 構造化配列を Table に入れると自動で NdarrayMixin に変換される処理を、構造化 Column が使えるようになったので外したい、という提案 | 1 ファイル。7 行削除のみ | FAIL_TO_PASS 2 件、PASS_TO_PASS は数百件 |

  - 自分なら解けるか：1 件目は、修正は 1 行だが、astropy のモデル合成と分離可能性の行列の考え方を理解しないと、どこを直すか分からない。2 件目は、エラー文の組み立て方を読めば直せそうだと思った。3 件目は、何を消すかは文面から推測できるが、テストが期待する警告や挙動までは issue から読み取りにくい。
  - LLM が解くときに難しい点：大きなリポジトリから直す場所を探すこと、issue の文面には書かれていないテストの期待（関数名やエラー文の細部）に合わせること、修正で既存のテスト（PASS_TO_PASS）を壊さないこと。

  作成と検証の手順

  | 段階 | 内容 |
  |---|---|
  | 元の SWE-bench（2023） | 人気のある Python のリポジトリ 12 個から約 90,000 件の PR を集めた。「issue を解決している」「テストファイルを変更している」マージ済みの PR に絞り、PR のテストを適用して「失敗から成功に変わるテストが 1 件以上ある」「インストールや実行のエラーがない」ものを残した。結果は 2,294 件。作問は人ではなく、GitHub の実際の issue と PR から自動で作った |
  | Verified の検証（2024） | Python の経験があるソフトウェア開発者 93 人が、テストセットから無作為に選んだ 1,699 件を確認した。1 件ごとに別々の 3 人が、「issue の説明が足りているか」「FAIL_TO_PASS のテストが正しい解答まで落としていないか」を 0〜3 の 4 段階（2 以上が重大）で付け、ほかの重大な問題（簡単にごまかせるテストなど）も記入した。修正にかかる時間の見積もりで難易度も付けた |
  | 落とした件数 | 3 人の中で最も重い判定を採用した。説明不足で 38.3%、テストが正しい解答を落としうることで 61.1% に印が付き、全体で 68.3% を除外した。残りから、1〜4 時間と 4 時間以上の問題をできるだけ残し、あとは無作為に選んで 500 件にした（15 分未満が 196 件、1 時間超が 45 件） |
  | 採点の方法 | モデルが作ったパッチを適用し、FAIL_TO_PASS（issue が直ったか）と PASS_TO_PASS（ほかを壊していないか）の両方のテストが通れば解決とする。人や LLM は採点しない |

  - 効果：GPT-4o（2024-05-13）の解決率は、元の SWE-bench の 16% に対し、Verified では 33.2% だった（OpenAI のブログ）。問題の不備で落ちていた分が取り除かれたためと説明されている。

- 気づき・疑問：
  - SWE-bench は「テストで機械的に採点できる」ことが強みだが、そのテスト自体が不公平だと、正しい解答も不正解になる。Verified で 61% にテストの問題の印が付いたことから、採点を自動化しても、採点の基準が正しいかは人が確認する必要があると分かった。今日の演習で、LLM の採点を人のラベルと比べたのと同じ考え方だと感じた。
  - Verified は 3 人のうち最も厳しい判定で除外していて、「人同士で割れる問題は使わない」方針になっている。今日の評価セットは、逆に割れる項目を残して観察している。ベンチマークは順位を付けるために曖昧さを減らし、今日のセットは基準を直すために曖昧さを見つける、という目的の違いだと考えた。
  - 1 件目のように、正解のパッチは 1 行でも、そこに着くまでに必要な知識が多い。正解の大きさと問題の難しさは比例しないので、難易度を「修正にかかる時間」で人が見積もったのは理にかなっていると思った。
  - 疑問：issue や修正が公開されているので、モデルが学習中にこの答えを見ている可能性（汚染）をどう扱っているのか。また、3 件とも astropy だったが、500 件の中でリポジトリの偏りはどの程度あり、それが結果に影響するのか。
  - 調べられなかったこと：12 個のリポジトリの名前と、難易度の区分ごとの全件数（ブログでは図になっていて、文章からは読めなかった）。
